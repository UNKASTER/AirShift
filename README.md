# 航勤智排（AirShift）

AirShift 是面向航司地面服务保障人员的单用户 Android 排班助手。它在手机本机识别排班图片或 Excel，只留下当前用户的保障任务；在用户自行配置 API Key 后，手机会直接查询飞常准 Aviation MCP，并把实时航班、提醒、MUC 特服信息和当前执勤集中到一个界面中。它还按上三休三周期推算未来的上班日、班次和应乘班车。

- 当前版本：`0.11.2`（version code `50`）
- 最低系统：Android 13（API 33）
- 项目形态：单模块、端侧优先、无自建后端

本文是使用与开发入口；完整业务规则、数据模型、并发保护和已知风险见 [spec.md](spec.md)。

## 项目解决什么问题

AirShift 把一张面向多人、包含多架飞机的日排班，转换成某一名保障人员可执行的任务序列：

- 从排班图片、`.xls` 或 `.xlsx` 中筛选当前用户的接机、送机和过站任务；
- 合并计划、预计、实际时间，以及登机口、机位、机号、机型和机场信息；
- 始终把“当前未完成执勤”和“下一项未完成执勤”作为主要工作窗口；
- 根据进港前 15 分钟或纯出港前 1 小时 10 分钟安排本地提醒；
- 可选读取 MUC 的新通知，在本机提取特服、登机口/机位变更和取消事件；
- 通过桌面小组件查看并完成当前执勤；
- 按上三休三周期推算哪天上班、当天是早几/中几/晚几，以及该坐哪趟班车。

项目明确不提供账号体系、云同步、团队调度、自建服务器、共享 API Key、iOS/Web 客户端或应用商店发布流程。没有飞常准 API Key 时，排班导入、离线查看和基于表内时间的提醒仍可使用。

## 五分钟上手

1. 在 Android 13 或以上设备安装 Debug APK，并首次打开应用。
2. 输入排班表中的姓名。去除首尾空格后需为 2–20 个字符；姓名保存在应用私有数据中，直到修改、清除应用数据或卸载。
3. 进入“全部执勤”，从系统图片选择器导入排班截图，或从系统文件选择器导入 `.xls` / `.xlsx`。也可以在 WPS 等应用中把单个 Excel 文件分享给“航勤智排”。
4. 如需实时航班，在“设置”中输入自己的飞常准 API Key。测试连接前必须先有一条包含航班号的排班。
5. 按需要授予通知、定位和精确闹钟权限；MUC 通知读取是另一项独立的系统特殊授权，只有主动开启后才工作。
6. 回到“当前执勤”查看到位倒计时、当前任务和下一任务；执行完成后点击“执勤完成”。
7. 如需桌面入口，在系统“小组件/应用挂件”列表中添加“当前执勤”。

> 重要：一次成功解析会用新结果整体替换旧排班并重置人工完成进度。即使文件格式正确、但没有匹配到当前姓名，成功结果也可能是空排班；只有读取或解析抛错时旧排班才会保留。

## 页面与日常操作

| 页面 | 主要用途 |
|---|---|
| 全部执勤 | 导入图片/Excel、查看状态与警告、手动下拉刷新；任务分"当前 / 接下来 / 已完成"三个栏位，点条就地展开细节 |
| 排班日历 | 按上三休三周期查看上班日、休息日、当天班次和应乘班车 |
| 当前执勤 | 板面倒计时、当前任务（展开）与下一任务（折叠）、完整特服和变更详情；"执勤完成"钉在底部 |
| 设置 | 修改姓名，测试/保存/清除飞常准 API Key，开启 MUC 通知读取并查看最近识别状态，调整排班日历的班组与到位余量 |

应用冷启动、进程重建或真正从后台恢复时会回到"当前执勤"；旋转等配置变化会保留当时选中的页面。

界面是"航显板 × 进程单"：每页顶部是贯通到状态栏之下的藏青板面（实时钟、日期、倒计时或班次），下面是冷白条架，每项任务是一条固定列的信息条（时间｜航班｜航线｜机位｜状态灯），左侧夹条给方向（进港蓝、出港红、过站上蓝下红）。东航红只用于出港与主操作；琥珀与墨绿只做状态灯。缺失数据显示"—"，不用灰色骨架。所有数字用内置的 Barlow 等宽数字字体，倒计时逐位翻牌。切换分区、展开任务条、底栏红灯横移都用无回弹弹簧从第一帧起步、在 200 ms 内完成，旧内容比新内容更快退场。支持跟随系统的深色模式，深色是真正的夜间航显配色而不是反色。

## 排班导入

### 图片 OCR

- 使用 Android 系统图片选择器，不申请整个相册或存储权限。
- 使用内置 PP-OCRv6 tiny、ONNX Runtime 和 OpenCV 离线识别；原图不上传。
- 按 9 列排班模板、表头位置、机号锚点和 Y 坐标聚类恢复数据行。
- 人员栏去除空白和标点后，必须包含配置姓名的完整规范化文本；不会使用单字模糊匹配。当前包含匹配仍可能让短姓名命中更长姓名，见“已知限制”。
- 仅从表格右侧的 `VIP/要客` 附加区提取航班号，并只在匹配到的个人任务上保存 VIP 布尔标记。

### Excel

- 手动导入和 Android 文件分享共用同一解析链路。
- 不信任扩展名或 MIME：OLE 文件签名进入 `.xls`，ZIP 文件签名进入 `.xlsx`，其他内容拒绝。
- 按表头语义识别机号、航班、时间、前后站和人员列，支持多个有效工作表、1900/1904 日期系统、文本/数值时间、Excel 日期序列和 `+` 次日标记。
- 有分隔符的人员名单逐项精确匹配；无分隔符的组合签名只有在长度足够且包含完整姓名时才匹配。
- Excel 的 `VIP信息/要客信息` 区域也会被扫描，最终仍只保存匹配任务上的 VIP 布尔标记。
- `.xls` 先写入应用私有缓存临时文件并用 HSSF 事件流读取，文件上限 256 MiB；`.xlsx` 对单个相关 XML、相关 XML 总量和工作表数量设有上限。完整边界见 [spec.md](spec.md#52-excel-导入)。

### WPS/Android 分享

分享入口只处理 `ACTION_SEND`、标准 `.xls/.xlsx` MIME、单个 `EXTRA_STREAM` 和获授权的 `content://` URI。它拒绝网页/文本链接、`file://`、多文件分享以及不支持的协议；应用无法判断一个合法 ContentProvider 是否在底层按需下载了云端文件。

分享事件按 FIFO 处理，重复 URI 不会被折叠。首启分享会先等待姓名设置。待处理 URI 仅随 Android `SavedStateHandle` 尝试恢复，未取得永久 URI 授权，因此强制停止、来源撤销授权或系统未保存状态时不保证恢复。

## 排班日历

排班日历是导航栏第 2 页，**完全由本机计算得出**，不需要当天已导入排班，也不联网。

### 周期与班次

- 六天一个周期：整班 3 天、交接班上午 1 天、休息 2 天；锚点为 2026-08-23（第 1 天）。
- 10 个在编班组按固定环形顺序 `1 → 5 → 11 → 8 → 9 → 2 → 6 → 4 → 10 → 3` 轮转，**每个整班工作日左移 3 位**；交接班日与休息日不推进轮转。
- 旋转后的位置直接对应班次槽位：前 3 位是早一–早三，中间 4 位是中一–中四，末 3 位是晚一–晚三。槽位号越小下班越早。
- 交接班日只上上午，班次沿用前一个整班工作日；**那天排到晚班的组干到次日凌晨，交接班上午不到岗**，日历会明确标出。

“我”是谁由设置中的姓名决定。内置班组表只有组号与轮转顺序，不含任何成员名单；导入过带“候机早班/中班/夜班”行的 Excel 后，姓名去除空白与括号备注需与校准得到的某个成员整名相同（短姓名不会误命中更长的姓名），否则请在设置中手动指定班组。

### 班车

- 发车时刻：`04:50`、`05:25`、`05:55`，其后自 `08:00` 起每两小时一班；交接班相关日（接班的第 1 天与交班的第 4 天）额外一班 `09:00`。车程约 5 分钟。
- 到位要求：出港航班最晚提前 70 分钟到位，进港航班最晚提前 15 分钟到位（与当前执勤页同一套规则）。
- 选车 = 满足「发车 + 车程 ≤ 到位时间 − 到位余量」的最晚一班。到位余量可在设置中选 0 / 15 / 30 分钟，默认 15。
- 固定习惯优先于推算：第 1 天早班/晚班坐 `09:00`、第 1 天中班坐 `12:00`；第 2、3 天的中二至中四坐 `12:00`。

### 预估与自校正

- 日历行标注“预估”时，首个任务时间取自实测规律；与已导入排班同一天的那一行改用真实航班时间并标注“按当日排班”。
- 导入带“候机早班/中班/夜班”行的 Excel 时，应用会读出当天真实的分组顺序与成员，用来校正班组表和轮转相位（病假、人员调整都能自适应）。解析不到该行时（图片导入、交接班日的半天表格）保持上一次校准结果不变。成员名单只保存在本机的校准数据里，不在应用源码中。

## 执勤、完成与实时刷新

每项 `RosterAssignment` 可包含一个进港航段、一个出港航段或两者组成的过站任务。

- 航段有实际到达/起飞时间时自动完成；否则以预计时间优先、计划时间回退，超过 3 小时后自动完成；完全没有可用时间也视为完成。
- 同一航班号每天都飞，但排班里的那一班只有一个：合并实时数据时，与计划时间相差超过 12 小时的航段（典型是别的日子的同号航班）整段丢弃、任务保持原值；自动完成与提醒同样只信同一班的预计时间。
- 飞常准按出发日查询：夜班里次日 06:00 前到达的进港航班按前一天查询，才能拿到排班里的这一班而不是下一班。
- 过站任务需要进、出港两段都完成。
- 人工完成以按执勤日保存的“已完成前缀”推进；执勤日在 06:00 切换（夜班跨零点后的完成不会被清零），进入新执勤日或导入新排班时重置，普通实时刷新不重置。
- 当前任务和下一任务都会跳过人工完成项及自动完成项。
- 完成按钮用排班 generation 和当前索引双重校验，旧页面或重复点击不会误完成下一项；但没有撤销或二次确认。

实时查询使用以下范围：

| 触发方式 | 查询范围 |
|---|---|
| 导入后的首次查询 | 当前未完成执勤 + 下一项未完成执勤 |
| 前台自动刷新 | 同一两项窗口，目标间隔 5 分钟 |
| WorkManager 后台刷新 | 同一两项窗口，系统调度周期至少 15 分钟，首轮延迟 15 分钟或直接延迟到排班日的跟踪起点 |
| 尚有未完成任务时手动下拉 | 同一两项窗口 |
| 全部任务完成后手动下拉 | 全排班航班；这是唯一的全量查询路径 |
| 人工完成后补查 | 只查新进入两项窗口的航班 |

这里没有旧版的“计划时间前后若干小时”筛选。两项任务最多展开 4 个航段，并按“航班号 + 运行日期”去重。全部任务完成后停止前后台自动刷新；显式手动下拉仍保留，并可能用修正后的实时数据（与计划相差 12 小时内）让自动完成项重新进入工作窗口。

自动刷新只在排班当天进行。App 只保存一份排班，它就是你上班那天的进程单：从首个任务前 3 小时起、到全部任务完成为止，导入后首刷、前台自动刷新、后台周期刷新和完成补查才会发起查询。排班日之外——休息、请假，或者头天晚上提前导入——不会自动联网，后台周期任务的首轮也直接延迟到跟踪起点；提前导入时状态栏会写明“M/d HH:mm 起自动跟踪航班动态”。显式手动下拉不受此限制。

手机进程内对成功的同航班同日期结果缓存 120 秒，并使用每分钟 30 次的滑动窗口保护。缓存命中、测试连接和随后因窗口变化而跳过的调用也会先占用本地限流容量；缓存与限流在进程重启后清空。部分请求失败时保留成功结果和旧数据，错误信息经过固定文本脱敏。

## 飞常准端侧直连

手机固定通过 HTTPS 请求飞常准 Aviation MCP 的 `searchFlightsByNumber`，只发送航班号、运行日期和 MCP 协议字段，不经过自建服务。API Key 仅作为 `X-API-Key` 请求头发送，并以 Android Keystore 管理的 AES-GCM 密钥加密保存在应用私有存储中；明文不会进入 saved-instance-state、源码、资源、`BuildConfig`、测试样例或 APK。

客户端可读取普通 JSON-RPC 或 SSE 外层，并处理多经停航班的逐航段结果。当前使用的主要字段包括计划/预计/实际起降时间、实际离位、登机口关闭观察、登机口、进出港机位、廊桥和机场坐标；精确映射见 [spec.md](spec.md#73-协议与字段映射)。

清除 API Key 会清空进程内航班缓存并停止后台实时刷新，但不会删除已保存排班。

## 提醒、定位与 MUC

### 本地提醒

- 有进港航段（包括过站）时，只安排预计/计划到达前 15 分钟的一条接机提醒。
- 纯出港任务安排预计/计划起飞前 1 小时 10 分钟的一条提醒。
- 已有对应实际时间、没有可用时间或触发点已过去时不安排。
- 提醒时间只来自任务自己的计划时间和同一班（与计划相差 12 小时内）的预计时间，因此只会落在排班那一天；休息日、请假日不会再收到同号航班的提醒。
- 有精确闹钟特殊访问时使用精确闹钟；否则退化为非精确闹钟并提示可能存在偏差。
- 开机后重新读取排班并恢复提醒，同时重绘小组件。

当前人工“执勤完成”不会从提醒策略中排除该任务：如果提前完成且提醒时间尚未来临，该提醒仍可能触发，开机后也可能被重排。这是已知实现边界。

### 机场定位

应用使用 Google Play Services 融合定位；精确权限对应高精度请求，只有粗略权限时使用平衡功耗精度。它只把当前位置与本次成功刷新范围中的候选机场比较，15 km 内才显示匹配结果；当前位置不会写入排班存储或由应用发送给飞常准。拒绝定位不影响排班查看。

### MUC 通知识别

通知读取必须由用户在系统设置中主动开启。系统授予的是通知监听特殊访问，但业务代码在提取正文前只接受包名严格等于 `com.ceair.im.muc` 的新通知；不读取 MUC 数据库、历史消息、通知移除事件、图片附件或无障碍界面。

应用可识别残障旅客、WCHR/WCHS/WCHC（也接受 MUC 口语简称 C轮/R轮/S轮）、UM、MAAS、客舱宠物、登机口/机位变更、特服取消和行程取消。高置信特服自动关联；低置信特服直接忽略。任务卡上的轮椅记录不显示 WCHR/WCHS/WCHC 全称，只显示轮椅图标加等级字母 C/R/S。特服、变更和取消在暂时没有匹配排班时都会保留最多 24 小时，并在排班变化后重试。航班主要按完整数字部分和日期匹配；消息带承运人且存在精确候选时优先承运人。

MUC 原文只在内存中解析。持久化内容是航班、日期、结构化结果、处理状态和本机密钥生成的 HMAC 指纹，不含通知原文、姓名、发送人、电话、票号、座位、图片或附件。

## 桌面小组件

“当前执勤”小组件是一个固定单卡，不支持翻页：

- 藏青板面，显示当前未完成任务、到位倒计时、VIP、进出港航班、对方机场和本站机位；
- 点击卡片打开应用，点击描边的“完成”原子推进当前任务并只补查新进入窗口的航班；
- 倒计时由 launcher 的 `Chronometer` 渲染，应用进程无需每秒唤醒；
- 导入、完成、实时刷新、提醒触发、开机和系统 30 分钟周期都会重绘；
- 小组件固定藏青配色（浅深壁纸都可读），默认 4×3，可缩放；OriginOS 中属于标准“应用挂件”，不是厂商专有“原子组件”；
- 小组件只读排班存储，不叠加 MUC 的登机口/机位变更或取消状态。

倒计时跨过零点后的即时显示由系统 `Chronometer` 决定；最迟在下一次主动或周期重绘时切换为“应立即到位”。

## 技术架构

```text
系统图片选择器 ─→ ImageDecoder ─→ PP-OCRv6 / ONNX Runtime / OpenCV ─┐
系统文件/分享 ─→ 文件签名 ─→ XLS 事件流 / XLSX SAX ───────────────┤
                                                                  ↓
                                                      RosterParseResult
                                                                  ↓
                                       RosterStore.replaceAssignments
                                           generation++ / 进度重置
                                          ┌──────┬──────┬──────┬──────┐
                                          ↓      ↓      ↓      ↓      ↓
                                      Compose  MUC重匹配 提醒  WorkManager 小组件

飞常准 HTTPS MCP ─→ 缓存/限流/批次 ─→ generation + scope 校验 ─→ RosterStore 合并
MUC 新通知 ─→ 白名单/提取/解析/归并 ─→ SpecialServiceRepository ─→ Compose
```

`MainActivity` 只负责装配依赖、接收分享 Intent 和转发生命周期；业务编排在 `duty/DutyViewModel`，它只依赖 `duty/DutyPorts` 里的端口接口，因此可以在 JVM 上用假实现测试；`ui/AirShiftApp` 只渲染状态并转发用户动作。项目没有引入导航框架或依赖注入框架。生产代码根目录是 `app/src/main/java/com/bradj/airshift/`，下表中的短路径均相对于它：

| 路径 | 职责 |
|---|---|
| `duty/` | 编排层：`DutyViewModel`、`DutyUiState`、端口接口与生产装配 `AppDutyPorts` |
| `model/` | 排班模型、自动完成、当前/下一窗口、执勤时间线 |

## 权限与数据

| 权限或特殊访问 | 用途 | 不可用或未授权时的行为 |
|---|---|---|
| `INTERNET` | 飞常准实时航班 | 只能使用导入/缓存数据 |
| 粗略/精确定位 | 匹配当前刷新范围内的机场 | 排班仍可查看，不显示自动机场匹配 |
| `POST_NOTIFICATIONS` | 弹出保障提醒 | 排班和闹钟状态仍保存，但系统不展示通知 |
| `SCHEDULE_EXACT_ALARM` | 更准时的本地提醒 | 退化为非精确闹钟 |
| `RECEIVE_BOOT_COMPLETED` | 开机后恢复提醒和小组件 | Manifest 固定声明，无运行时弹窗 |
| 通知读取特殊访问 | 读取 MUC 新通知 | MUC 识别关闭，其他功能不受影响 |

图片和 Excel 使用系统选择器，不申请整个相册或通用存储权限。Manifest 禁止应用数据云备份和设备迁移；姓名、匹配任务、任务人员栏、实时字段、进度、API Key 密文和结构化 MUC 状态都只保存在应用私有区域。原图片/Excel 不会持久化或上传，`.xls` 的解析临时文件会在 `finally` 中删除。

## 构建、运行与测试

### 环境

- JDK 17；
- Android SDK 37；
- Android Studio 或 PowerShell 7；
- Android 13（API 33）以上设备/模拟器用于安装和仪器测试。

Gradle Wrapper 为 9.5.0，Android Gradle Plugin 为 9.3.0，Kotlin 为 2.4.10。Android Studio 通常会在未跟踪的 `local.properties` 中写入 `sdk.dir`。项目位于 OneDrive 时，可额外把构建目录放到本地磁盘：

```properties
sdk.dir=C:/Users/<you>/AppData/Local/Android/Sdk
airshift.buildDir=C:/Users/<you>/AppData/Local/CodexBuild/AirShift
```

PowerShell 7：

```powershell
$env:JAVA_HOME = '<JDK 17 或 Android Studio JBR 路径>'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
.\gradlew.bat test lintDebug detekt assembleDebug
```

Gradle 守护进程固定使用 JDK 21（`gradle/gradle-daemon-jvm.properties`，首次运行时经 foojay 自动下载），因此 `JAVA_HOME` 指向 Android Studio 自带的 JBR 25 也没关系；`compileOptions` 仍是 Java 17。Android Lint 与 detekt 各有一份基线文件（`app/lint-baseline.xml`、`app/detekt-baseline.xml`）：既有发现不阻塞构建，新增的 warning 或 detekt 发现会让对应任务失败。`.github/workflows/ci.yml` 在 push 到 `main` 与 PR 时执行同样的单元测试、Lint 和 detekt。

默认 APK 位于 `app/build/outputs/apk/debug/app-debug.apk`；配置 `airshift.buildDir` 后位于 `<airshift.buildDir>/app/outputs/apk/debug/app-debug.apk`。连接设备后可安装或执行 Android 测试：

```powershell
.\gradlew.bat installDebug
.\gradlew.bat connectedDebugAndroidTest
```

仪器测试中的 OCR 端到端用例使用仓库内无真实个人信息的 `testdata/synthetic_roster.png`。可选真实 `.xls` fixture 需配置 `AIRSHIFT_XLS_FIXTURES_DIR` 与 `AIRSHIFT_XLS_TEST_NAME`，默认跳过。

当前源码包含 285 个 JVM `@Test` 和 62 个 Android `@Test`（其中 1 个是默认跳过的付费飞常准查询探针，需显式开启）。覆盖排班解析、完成与窗口规则、排班周期与班组轮转、班车规则、飞常准载荷/缓存/限流、多经停映射、MUC 状态机、导航/前台刷新、generation 竞态、WPS 分享、小组件和合成 OCR；这两个数字是测试方法规模，不等同于某次运行结果。本轮验证快照见 [spec.md](spec.md#122-本轮验证)。

## 已知限制

- 只支持单用户、单份当前排班和中文硬编码界面；无账号、云同步、团队调度或多语言。
- 内置班组表不含成员姓名：在导入过带班次行的 Excel 之前，排班日历无法按姓名自动识别班组，需要在设置中手动指定。
- Keystore 瞬时故障时 API Key 本次读取为空、后台刷新跳过本轮，但密文保留，稍后自动恢复；只有认证标签不符、密钥失效或密文损坏才会清除。
- 排班日历的轮转步长、槽位分层和交接班到岗规则由 2026-08-24 至 09-01 的六份实测排班表反推，样本内零反例但属外推；长期漂移依赖导入 Excel 时的自校正。
- 排班日历只有与当前已导入排班同一天的那一行能用真实航班时间，其余行是按实测规律的预估值。
- 图片解码没有文件大小、像素或内存上限；超大图片可能导致内存压力。
- OCR 人员栏使用“包含完整规范化姓名”，短姓名可能命中更长姓名；Excel 的分隔符感知匹配更严格。
- 成功解析但零匹配会替换旧排班；UI 当前没有导入前确认或回滚。
- WPS 分享队列无显式长度上限，恢复依赖 Android 保存状态和临时 URI 授权，不保证强停后的 exactly-once。
- 预计/计划时间超过 3 小时即自动完成，陈旧预计时间或超长延误可能让任务过早退出窗口；与计划相差超过 12 小时的预计时间会被当成别的日子的同号航班而不采用。
- 排班日以外不自动跟踪：跟踪时段以排班自身的日期为准。排班没有识别出日期时按导入当天处理，若在头天晚上导入，跟踪与提醒都会落在错误的一天，需要重新导入带日期的表。
- 凌晨出发、凌晨到达的红眼航班会被按前一天查询并被 12 小时归属规则拒绝，只有计划时间、没有实时数据；没有换一天重试的逻辑。
- 人工完成不可撤销，且不会取消该任务尚未触发的提醒。
- WorkManager 的 15 分钟是最小请求周期，实际后台运行可能被系统延后。
- 飞常准内层载荷是类 Python 字典文本，当前用受限解析器读取；上游格式或转义变化可能导致失败。
- 相同 generation 的重叠刷新没有服务端时间戳排序，同字段以最后一次写入为准。
- 任一损坏的排班 JSON 条目可能让整份排班加载为空；MUC JSON 则逐项跳过损坏记录。
- MUC 数字航班简写没有最大日期距离阈值；跨承运人同数字时会稳定选择一个候选，而不是要求人工确认。
- MUC 的 24 小时过期先在逻辑查询中隐藏，物理清理要等下一次通知或排班重匹配。
- 小组件不显示 MUC 变更；跨零点状态与不同 launcher 的裁剪行为仍需持续观察（vivo OriginOS 4×3 已核对，Barlow 字体在桌面进程中解析正常）。
- Barlow Semi Condensed 的 tabular 数字宽度仍有约 7% 差异，倒计时与时钟因此用固定位宽的翻牌槽位；信息条里的时间列允许这点差异。
- `arrivalBridge` 已解析并持久化，但当前 UI 未展示；提醒 ID 使用 32 位 `stableId.hashCode()`，理论上可能碰撞。
- 真实飞常准、真实 WPS/MUC、ContentProvider 授权、定位、闹钟、通知和锁屏流程仍需物理设备端到端验证。
- 仓库有 GitHub Actions（单元测试 + Android Lint + detekt），但没有发布签名或商店分发配置；release 已开启 R8 压缩，但未签名、未在真机验证，Debug APK 仍是唯一可安装的产物。
